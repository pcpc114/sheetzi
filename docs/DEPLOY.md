# 시트지 배포 안내서 — 아무것도 없는 상태에서 `https://xotks.li` 까지

이 문서는 **개발을 모르는 사람이 그대로 따라 하면 끝나도록** 쓴 것입니다.
위에서부터 순서대로, 한 단계씩 하세요. 건너뛰지 마세요.

목표 상태는 이렇습니다.

- 주소창에 `https://xotks.li` 를 치면 자물쇠가 달린 채로 시트지가 열린다
- 비밀번호를 모르는 사람은 아무것도 못 본다
- 입력한 내용은 **Supabase 데이터베이스**에 저장된다 (서버를 다시 배포해도 남는다)

준비물:

| 준비물 | 상태 |
|---|---|
| 이 프로젝트 폴더 (`C:\Users\B\Desktop\시트지`) | 이미 있음 |
| Node.js (내 컴퓨터에 설치되어 있어야 함) | 이미 있음 |
| Supabase 프로젝트 + 표 3개 (`sz_documents`, `sz_journal`, `sz_backups`) | **이미 만들었음** |
| 도메인 `xotks.li` | **이미 샀음** |
| Cloudflare 에 네임서버 연결 (`braelyn` / `derek.ns.cloudflare.com`) | **이미 끝났음** |
| GitHub 계정 | 없으면 지금 만드세요 (무료) |
| Render 계정 | 없으면 지금 만드세요 (무료) |

처음 하면 **40분에서 1시간** 정도 걸립니다. 그중 절반은 기다리는 시간입니다.

> **이 문서에서 가장 중요한 한 줄**
>
> 배포가 끝나면 반드시 Render 의 **Logs** 를 열어
> `[시트지] 문서 저장소: Supabase (...)` 라는 줄이 있는지 눈으로 확인하세요.
> 여기에 `파일 (data/ 디렉터리)` 라고 적혀 있으면 **사이트는 멀쩡해 보이는데
> 다음 배포 때 문서가 전부 사라집니다.** 자세한 내용은 6단계에 있습니다.

## 1단계 — 비밀번호 해시 만들기

사이트 전체를 잠그는 **공유 비밀번호 하나**를 정합니다. 이 비밀번호를 아는 사람은
모든 문서를 읽고 쓸 수 있습니다 (사람별 구분은 없습니다).

비밀번호를 Render 화면에 **그대로 적지 않고**, 되돌릴 수 없는 한 줄(해시)로 바꿔서
넣습니다. 그러면 나중에 그 화면을 누가 보더라도 비밀번호를 알아낼 수 없습니다.

1. 시작 메뉴에서 **PowerShell** 또는 **터미널** 을 엽니다.
2. 아래를 한 줄씩 붙여넣고 Enter:

   ```
   cd "C:\Users\B\Desktop\시트지"
   node tools\hash-password.mjs
   ```

   > `npm run hash-password` 도 같은 일을 하지만, 윈도우는 기본 설정에서 npm 의 스크립트
   > 파일 실행을 막습니다. 그때는 이런 빨간 글씨가 납니다:
   >
   > ```
   > npm : 이 시스템에서 스크립트를 실행할 수 없으므로 ... npm.ps1 파일을 로드할 수 없습니다.
   > ```
   >
   > 위처럼 `node` 로 직접 실행하면 npm 을 거치지 않으므로 이 문제가 아예 생기지 않습니다.
   > 윈도우 보안 설정을 바꿀 필요도, 나중에 되돌릴 것도 없습니다. 이 문서의 다른 `npm`
   > 명령에서 같은 오류가 나면 `npm run X` 를 `node tools\X.mjs` 로 바꿔서 실행하세요.

3. `비밀번호:` 라고 나옵니다. **화면에는 아무 글자도 안 보입니다. 정상입니다.**
   비밀번호를 치고 Enter, 그다음 `비밀번호 확인:` 에 같은 걸 다시 치고 Enter.
4. 이런 줄이 나옵니다:

   ```
   아래 한 줄을 서버 환경 변수 SZ_PASSWORD_HASH 에 넣으세요 ...
   scrypt$16384$8$1$AbCdEfGhIjKlMnOp==$QrStUvWxYz0123456789abcdefghijkl=
   ```

   (위 값은 **모양만 보여 주는 예시**입니다. 실제 값은 방금 화면에 나온 것을 쓰세요.)

5. `scrypt$` 로 시작하는 **그 한 줄 전체**를 복사해서 메모장에 임시로 붙여넣어 두세요. **저장하지 마세요** — 6단계에서 Render 에 옮겨 넣고 나면 그 창은 닫습니다(11단계 확인표).
   5단계에서 씁니다.

**주의사항**

- 그 줄은 `$` 기호를 포함하고 끝이 `=` 로 끝날 수 있습니다. **끝의 `=` 까지 전부**
  복사해야 합니다. 하나라도 빠지면 서버가 아예 안 켜집니다 (그건 오히려 다행입니다.
  잠금이 조용히 풀리는 것보다 낫습니다).
- 정한 비밀번호 자체도 따로 안전한 곳에 적어 두세요. 해시에서는 되돌릴 수 없습니다.
- 위 2~4번(물어보면 입력하는 방식)이 **권장 방법입니다.** 비밀번호가 화면에도, 파일에도,
  어디에도 남지 않습니다. 되도록 이 방법만 쓰세요.

### 대안 — 물어보는 입력이 안 되는 터미널일 때

`이 터미널에서는 비밀번호를 가려서 입력할 수 없습니다` 라는 줄이 나오는 터미널이라면
비밀번호를 명령에 직접 적을 수 있습니다:

```
node tools\hash-password.mjs 내가정한비밀번호
```

**이 방법을 썼다면 아래 정리를 반드시 끝까지 하세요. 창을 닫는 것만으로는 안 지워집니다.**

PowerShell 은 사용자가 친 명령을 **파일에 적어 둡니다.** 창을 닫아도, 컴퓨터를 껐다 켜도
그 파일은 그대로 남습니다. 그래서 위 명령을 쓰는 순간, 사이트 전체를 지키는 비밀번호가
아래 파일 안에 **글자 그대로** 들어갑니다.

```
%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
```

지우는 순서 — **네 단계를 전부** 하세요:

1. 비밀번호를 친 그 창을 **닫습니다.** (닫아야 그 창이 기록을 다시 쓰지 않습니다)
2. PowerShell 을 **새로** 엽니다.
3. 아래 한 줄을 붙여넣고 Enter:

   ```
   Remove-Item (Get-PSReadLineOption).HistorySavePath
   ```

4. 그 창도 닫습니다.

이 명령은 그 기록 파일을 **통째로** 지웁니다. 지금까지 친 다른 명령 기록도 같이 사라집니다.
일부러 그렇게 합니다 — 비밀번호가 든 줄만 골라 지우려다 하나 놓치는 쪽이 훨씬 위험하기
때문입니다. 다음에 명령을 치면 그때부터 기록이 다시 쌓입니다. 정상입니다.
`경로를 찾을 수 없습니다` 라고 나오면 그 파일이 원래 없었던 것이니 그대로 넘어가세요.

> 명령에 적은 비밀번호는 그 순간 **실행 중인 프로세스 목록**에도 잠깐 보입니다. 그건
> 명령이 끝나면 사라지므로 따로 지울 것이 없습니다. 남는 것은 위의 기록 파일뿐입니다.

> **왜 `SZ_PASSWORD` 가 아니라 `SZ_PASSWORD_HASH` 인가?**
> 둘 다 됩니다. 하지만 `SZ_PASSWORD` 는 비밀번호를 **글자 그대로** Render 화면에
> 저장합니다. 인터넷에 공개하는 서버라면 해시 쪽을 쓰세요.
> **둘 다 넣으면 `SZ_PASSWORD_HASH` 가 이깁니다.** 그러니 해시를 쓸 거면
> `SZ_PASSWORD` 는 아예 만들지 마세요.

## 2단계 — 세션 서명 키 만들기

한 번 로그인하면 14일 동안 유지되는데, 그 "로그인 상태"에 위조 방지 도장을 찍는 데
쓰는 긴 임의 문자열입니다.

같은 터미널에서:

```
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

나오는 한 줄(글자와 숫자 64자쯤)을 복사해서 메모장에 임시로 붙여넣어 두세요. **저장하지 마세요** — 6단계에서 Render 에 옮겨 넣고 나면 그 창은 닫습니다(11단계 확인표).

> **안 넣으면 어떻게 되나:** 서버가 켜질 때마다 임시 키를 새로 만들고, 로그에
> `SZ_SESSION_SECRET이 없어 임시 서명 키를 만들었습니다 — 서버를 다시 시작하면
> 모두 로그아웃됩니다` 라는 경고가 나옵니다. 무료 요금제는 **잠들었다 깨어날 때마다**
> 다시 시작되므로, 이 값을 안 넣으면 하루에도 몇 번씩 다시 로그인해야 합니다.
> 꼭 넣으세요.

## 3단계 — Supabase 값 두 개 챙기기

Supabase 대시보드에서 프로젝트를 열고, 왼쪽 맨 아래 **`Project Settings`**(톱니바퀴)
를 누릅니다. 여기서 챙길 것은 **주소 하나**와 **비밀 키 하나**, 둘뿐입니다.

### 값 1 — 주소 (`SUPABASE_URL`)

**`Project Settings` → `Data API`** 화면 맨 위의 `Project URL` 입니다.
`https://<프로젝트이름>.supabase.co` 형태의 한 줄을 그대로 복사하세요.
(프로젝트 홈 화면 위쪽에도 같은 값이 있습니다.)

### 값 2 — 비밀 키 (`SUPABASE_SERVICE_KEY`)

**`Project Settings` → `API Keys`** 를 누릅니다. 화면에 칸이 두 개 있습니다.
**`Secret keys`** 쪽입니다.

| 화면에 보이는 칸 | 이걸 쓰나요 |
|---|---|
| **`Publishable key`** — `sb_publishable_...` 로 시작하고, 가려지지 않은 채 그냥 보입니다 | **아닙니다** |
| **`Secret keys`** — 줄마다 이름(`default` 같은)이 있고 값은 `sb_secret_...`, 점으로 가려져 있습니다 | **이것입니다** |

`Secret keys` 줄에서 이렇게 복사합니다.

1. 값이 `sb_secret_••••••••` 처럼 가려져 있습니다.
2. 값 오른쪽의 **눈 모양 아이콘**(`Reveal`)을 누릅니다. 가려진 부분까지 전부 보입니다.
3. 그 옆의 **복사 아이콘**(네모 두 장이 겹친 모양)을 누릅니다.
   마우스로 긁어서 복사하면 끝이 잘리기 쉬우니 꼭 이 버튼을 쓰세요.
4. 메모장에 붙여넣습니다. `sb_secret_` 로 시작하는 한 줄이면 맞게 가져온 것입니다.

> **`Secret keys` 아래에 줄이 하나도 없으면** `Create new secret key` 를 누르고 이름을
> 아무거나(`sheetzi` 같은) 지어 하나 만드세요. 만들자마자 위와 똑같이 복사하면 됩니다.

> **화면에 `Legacy anon, service_role API keys` 라는 탭도 보입니다.**
> 예전 방식의 키들이 있는 곳입니다. 거기 `service_role` 의 `eyJ` 로 시작하는 아주 긴
> 값도 시트지는 그대로 받습니다 — **둘 중 아무 쪽이든 하나면 됩니다.** 다만 Supabase
> 가 이 옛 키들을 **2026년 말에 없앨 예정**이라고 밝혔으므로, 지금 새로 넣는 값은
> `sb_secret_` 쪽을 쓰세요. 이미 옛 키로 돌아가는 서버가 있다면 **2026년 말 전에**
> `sb_secret_` 키로 바꾸세요 — 그때가 지나면 Supabase 가 옛 키를 없애서 서버가
> `Supabase 인증에 실패했습니다` 로 아예 켜지지 않습니다.

두 값을 메모장에 임시로 붙여넣어 두세요. **저장하지 마세요** — 6단계에서 Render 에 옮겨 넣고 나면 그 창은 닫습니다(11단계 확인표).

> 비밀 키(`sb_secret_...`, 또는 옛 `service_role`)는 데이터베이스 전체 권한입니다.
> **서버에만** 넣습니다.
> 위처럼 옮기는 동안 잠깐 메모장에 두는 것 말고는, 채팅·GitHub·공유 문서·스크린샷
> 어디에도 붙여넣지 마세요. 메모장 창은 6단계가 끝나면 **저장하지 말고 닫으세요.** 실수로 노출됐다면 Supabase 대시보드에서
> 즉시 새 키를 만들고(`Create new secret key`) 노출된 키를 `Revoke` 한 다음, Render 의
> 값도 새 키로 바꾸세요. 옛 `service_role` 키라면 같은 화면의 `Reset` 입니다.

> **`Publishable key` 나 옛 `anon` 키를 넣으면 어떻게 되나요?**
> 그 둘은 브라우저에 노출돼도 되는 **공개용** 키라서, 이 표 3개에는 권한이 하나도
> 없습니다(표 3개는 RLS 가 켜져 있고 통과 정책이 하나도 없습니다 — 일부러 그렇게 만든
> 설계입니다). 잘못 넣으면 시트지가 **켜지기 전에 알아보고 멈춥니다.** 로그에 이렇게
> 남습니다:
>
> ```
> [시트지] SUPABASE_SERVICE_KEY 에 공개용(publishable) 키가 들어 있습니다. 이 키에는 아무 권한이 없어 ...
> [시트지] 해결: Supabase 대시보드 → Project Settings → API Keys → Secret keys 에서 ...
> ```
>
> 사이트가 멀쩡히 뜬 채로 저장만 조용히 실패하는 일은 없다는 뜻입니다. SQL 을 다시
> 돌릴 필요도 없고, 키만 `Secret keys` 쪽 값으로 바꾸면 됩니다.

표 3개(`sz_documents`, `sz_journal`, `sz_backups`)는 이미 만들어 두셨다고 했으니
넘어갑니다. 혹시 확실하지 않으면 Supabase → **Table Editor** 에서 세 이름이 다
보이는지 확인하세요. 없으면 **SQL Editor → New query** 에 `docs/supabase.sql` 내용을
전부 붙여넣고 Run 하세요.

## 4단계 — 코드를 GitHub 에 올리기 (반드시 Private)

Render 는 GitHub 에 있는 코드를 가져다 실행합니다. 그래서 먼저 올려야 합니다.

가장 쉬운 방법은 **GitHub Desktop** 입니다.

1. <https://desktop.github.com> 에서 받아 설치하고 GitHub 계정으로 로그인합니다.
2. `File` → `Add local repository...` → `C:\Users\B\Desktop\시트지` 선택.
   "이 폴더는 Git 저장소가 아닙니다" 라고 나오면 **`create a repository`** 를 누릅니다.
3. `Publish repository` 를 누릅니다.
   **`Keep this code private` 체크박스를 반드시 켠 채로** 올립니다.

**왜 반드시 Private 인가 (읽고 넘어가세요)**

- `.env` 파일은 `.gitignore` 에 들어 있어 **올라가지 않습니다.** 그건 맞습니다.
- 그런데 `data/` 폴더 안의 **백업 파일(`start1.bak.1` 같은 것)** 은 지금 설정으로는
  걸러지지 않고 **같이 올라갑니다.** 그 안에는 지금까지 이 컴퓨터에서 만든 문서 내용이
  들어 있습니다. 저장소를 Public 으로 만들면 그 내용이 인터넷에 공개됩니다.
- Private 으로 만들면 이 문제는 없습니다. 그래도 신경 쓰인다면, 올리기 전에
  GitHub Desktop 왼쪽 파일 목록에서 `data/` 로 시작하는 항목의 체크를 모두 끄세요.

> `data/` 폴더는 이 컴퓨터에서 파일 방식으로 쓸 때 쓰는 폴더입니다.
> Supabase 를 쓰면 서버는 이 폴더를 **읽지도 쓰지도 않습니다.** 올라가더라도 서버 동작에는
> 영향이 없고, 순전히 "내용이 공개되느냐"의 문제입니다.

## 5단계 — Render 에 서비스 만들기

1. <https://render.com> 에 GitHub 계정으로 로그인합니다.
2. 오른쪽 위 **`+ New`** → **`Web Service`**.
3. **Git Provider** 에서 방금 올린 저장소를 고르고 `Connect`.
4. 아래처럼 채웁니다.

   | 항목 | 넣을 값 | 설명 |
   |---|---|---|
   | **Name** | `sheetzi` (아무거나) | 주소가 `sheetzi-xxxx.onrender.com` 이 됩니다 |
   | **Language** (예전 이름 Runtime) | `Node` | 보통 자동으로 잡힙니다 |
   | **Branch** | `main` | GitHub Desktop 이 만든 기본 이름 |
   | **Region** | **`Singapore`** | 한국에서 가장 가깝습니다 |
   | **Root Directory** | (비워 둠) | |
   | **Build Command** | `npm install` | |
   | **Start Command** | `npm start` | |
   | **Instance Type** | **`Free`** | |

   **Build Command 와 Start Command 는 위와 정확히 같아야 합니다.**
   이 프로젝트는 컴파일이나 빌드 과정이 없습니다. `npm install` 은 `express` 와 `ws`
   두 개를 받아오는 것뿐이고, `npm start` 는 `node server.js` 를 실행합니다
   (`package.json` 의 `scripts.start` 에 그렇게 적혀 있습니다).

5. **`Advanced`** 를 펼치고 **Health Check Path** 에 다음을 넣습니다:

   ```
   /healthz
   ```

   이 주소는 로그인 없이도 열리는 유일한 상태 확인용 주소입니다
   (`{"ok":true,"build":"..."}` 를 돌려줍니다). 넣어 두면 서버가 실제로 뜨기 전에
   Render 가 "배포 성공"이라고 판단하는 일이 없어집니다.

   이 칸을 못 찾겠으면 그냥 넘어가도 됩니다. 서비스를 만든 뒤 왼쪽 메뉴
   **`Settings`** 안에도 같은 항목이 있으니 거기서 나중에 넣으면 됩니다.

6. 같은 화면의 **Environment Variables** 에서 `+ Add Environment Variable` 을 눌러
   아래를 **하나씩** 넣습니다.

### 넣어야 하는 환경 변수

| 이름 | 값 | 필수? |
|---|---|---|
| `NODE_VERSION` | `22` | **필수에 가까움** (아래 설명) |
| `SZ_PASSWORD_HASH` | 1단계에서 복사한 `scrypt$...` 한 줄 | **필수** |
| `SZ_SESSION_SECRET` | 2단계에서 만든 임의 문자열 | **필수** |
| `SUPABASE_URL` | 3단계의 `https://<프로젝트이름>.supabase.co` | **필수** |
| `SUPABASE_SERVICE_KEY` | 3단계의 비밀 키 — `sb_secret_...` (또는 옛 `service_role`) | **필수** |

### 넣지 말아야 할 것

| 이름 | 이유 |
|---|---|
| `PORT` | Render 가 알아서 넣어 줍니다. 직접 넣으면 오히려 꼬일 수 있습니다 |
| `SZ_PASSWORD` | `SZ_PASSWORD_HASH` 를 넣었으므로 무시됩니다. **무시된다는 말은 로그에 안 나오므로** 넣은 사람은 그걸 알 수 없고, 비밀번호만 Render 화면에 그대로 남습니다 |
| `SZ_SESSION_DAYS` | 안 넣으면 14일입니다. 그대로 두세요 |
| `SUPABASE_SCHEMA` | 표를 `public` 이 아닌 곳에 만들었을 때만 필요합니다. 그대로 두세요 |

> **`NODE_VERSION` 을 왜 넣나요?**
> 이 프로그램은 Node 20.12 이상이 필요합니다 (`package.json` 의 `engines` 에 적혀
> 있습니다). Render 는 보통 알아서 최신 버전을 고르지만, 그 "알아서"가 언젠가 바뀌면
> 어느 날 갑자기 배포가 깨집니다. `22` 를 못 박아 두면 그 일이 없습니다.
> 내 컴퓨터와 똑같이 맞추고 싶으면 `24` 를 넣어도 됩니다.

7. **`Deploy Web Service`** 를 누릅니다. 3분에서 5분 걸립니다.

## 6단계 — 배포 로그 읽기 (여기가 제일 중요합니다)

Render 서비스 화면의 왼쪽 메뉴에서 **`Logs`** 를 엽니다.
Render 자신의 빌드 로그(`npm install ...`, `==> Your service is live` 같은 줄)가 앞뒤에
섞여 있습니다. 그중 **`[시트지]` 로 시작하는 줄만** 모으면 아래 8줄이어야 합니다.

### 제대로 된 로그

```
[시트지] 접근 제한이 켜져 있습니다 — 공유 비밀번호 하나로 사이트 전체를 보호합니다 (세션 14일).
[시트지] 문서 저장소: Supabase (xxxxxxxx.supabase.co) — 문서가 데이터베이스에 저장됩니다.
[시트지] Supabase 키 형식: 새 형식 비밀 키 (sb_secret_) — apikey 헤더로만 보냅니다.
[시트지] Supabase 테이블 확인 완료: sz_documents, sz_journal, sz_backups (스키마 public)
[시트지] 시작 문서를 만들었습니다: 시작 시트 (start1)
[시트지] 문서 1개를 불러왔습니다.
[시트지] 서버 실행 중 → http://localhost:10000
[시트지] 클라이언트 버전 xxxxxx
```

이 8줄 중 **1번과 2번, 두 줄만 확인하면 됩니다.**

- 1번이 `접근 제한이 켜져 있습니다` — 비밀번호가 걸려 있다는 뜻.
- 2번이 `문서 저장소: Supabase` — 데이터베이스에 저장한다는 뜻.

> **3번 줄(`Supabase 키 형식: ...`)은 어떤 키를 넣었는지 서버가 알아본 결과입니다.**
> 값은 절대 찍히지 않고 "어떤 형식인지"만 찍힙니다. 3단계에서 `sb_secret_` 키를
> 넣었으면 위와 똑같이 나오고, 예전 `service_role` 키를 넣었으면 대신 이렇게 나옵니다:
>
> ```
> [시트지] Supabase 키 형식: 레거시 JWT 키 (service_role) — apikey 와 Authorization: Bearer 두 헤더로 보냅니다.
> ```
>
> 둘 다 정상입니다. 형식마다 보내는 방식이 달라서 서버가 알아서 맞춘 것이고, 넣을
> 설정도 고를 것도 없습니다. 여기에 `공개 키` 나 `anon` 이라는 말이 보인다면 잘못된
> 키이고, 그 경우엔 아래 "무엇이 잘못될 수 있나" 3번 표로 가세요.

> `서버 실행 중 → http://localhost:10000` 은 **정상입니다.** 서버가 자기 자신을
> 부르는 주소를 찍은 것뿐이고, 실제로는 바깥에서 오는 접속을 모두 받는 상태로 열려
> 있습니다. 이 주소를 브라우저에 치는 게 아닙니다.
>
> 5번 줄 `시작 문서를 만들었습니다` 는 **처음 배포할 때만** 나옵니다. 두 번째부터는
> 그 줄 없이 `문서 N개를 불러왔습니다` 만 나옵니다. 그게 정상입니다.
### 최악의 경우 — 이 줄이 보이면 즉시 멈추세요

```
[시트지] 문서 저장소: 파일 (data/ 디렉터리) — 이 서버의 디스크에만 저장됩니다.
```

**이건 사이트가 멀쩡히 뜨고, 로그인도 되고, 편집도 되고, 화면에 `저장됨` 도 뜹니다.
그런데 다음에 배포하거나 서버가 다시 시작되는 순간 문서가 전부 사라집니다.**

이유: Render 무료 요금제에는 **영구 디스크를 붙일 수 없습니다.** 서버가 배포될 때마다,
다시 시작될 때마다, 잠들었다 깨어날 때마다 파일 시스템이 처음 상태로 돌아갑니다.
`data/` 폴더에 쓴 내용은 그때 같이 사라집니다.

원인은 딱 하나입니다: **`SUPABASE_URL` 환경 변수가 없거나 비어 있음.**

고치는 법:

1. Render → 서비스 → 왼쪽 메뉴 **`Environment`**
2. `SUPABASE_URL` 이 있는지, 값이 `https://` 로 시작하는지, 앞뒤에 따옴표나 공백이
   붙어 있지 않은지 확인
3. 고치고 `Save, rebuild, and deploy`
4. 다시 Logs 를 열어 2번 줄이 `Supabase` 로 바뀌었는지 확인

> **왜 이 하나만 조심하면 되나?**
>
> `SUPABASE_URL` 을 넣었는데 키가 틀렸거나, 주소에 오타가 있거나, 표가 없다면
> 서버는 **아예 켜지지 않고** 이유를 말하고 죽습니다 (아래 "무엇이 잘못될 수 있나"의
> 표 참고). 조용히 파일 방식으로 되돌아가는 일은 없습니다.
>
> 위험한 건 **`SUPABASE_URL` 자체를 빠뜨리는 경우 하나뿐**입니다. 그때만 시트지는
> "아, Supabase 를 안 쓰기로 했구나" 하고 정상적으로 파일 방식으로 켜집니다.

### 확실하게 두 눈으로 확인하는 법

로그를 믿기 어렵다면 Supabase 쪽에서 직접 보세요.

1. 사이트를 열어 로그인하고, 문서 목록에서 **`시작 시트` 카드를 눌러** 문서를 연 다음
   아무 칸에나 글자를 하나 칩니다. (로그인 직후 화면은 문서 **목록**이라 칸이 없습니다.
   7단계에 자세히 있습니다.)
2. Supabase 대시보드 → **Table Editor** → **`sz_documents`**
3. 줄(row)이 하나 이상 보이고 `rev` 숫자가 있으면 **데이터베이스에 저장되고 있는
   것**입니다.

## 7단계 — onrender.com 주소로 먼저 확인

도메인을 붙이기 **전에**, Render 가 준 주소로 먼저 확인합니다.
이렇게 하면 나중에 문제가 생겼을 때 "앱 문제"인지 "도메인 문제"인지 바로 구분됩니다.

Render 서비스 화면 맨 위에 `https://sheetzi-xxxx.onrender.com` 같은 주소가 있습니다.

1. 뒤에 `/healthz` 를 붙여서 엽니다. `{"ok":true,"build":"..."}` 가 보여야 합니다.
2. 이제 `/healthz` 없이 주소만 엽니다. **로그인 화면**이 나와야 합니다.
   (로그인 없이 문서 목록이나 스프레드시트가 나오면 비밀번호가 안 걸린 것입니다.
   6단계 1번 줄을 다시 보세요.)
3. 1단계에서 정한 비밀번호를 넣습니다. **`내 문서` 라는 문서 목록 화면**이 열립니다.
   **여기에는 칸(셀)이 없습니다. 정상입니다.** 시트지는 로그인하면 스프레드시트가 아니라
   문서 목록부터 보여 줍니다.
4. 목록에 **`시작 시트`** 카드가 하나 있습니다. **그 카드를 누릅니다.** 그제서야 칸이
   격자로 깔린 스프레드시트가 열리고, 주소 끝이 `/edit#doc=start1` 로 바뀝니다.
5. 아무 칸을 누르고 `123` 을 친 뒤 Enter 를 칩니다. 헤더의 저장 표시(`연결됨` 바로 왼쪽)가
   잠깐 `저장 중…` 이 되었다가 **`저장됨`** 으로 돌아옵니다. 너무 빨라 `저장 중…` 을
   못 볼 수도 있습니다. 마지막에 **`저장됨`** 이면 된 것입니다.
6. **브라우저를 새로고침(F5)** 합니다. `123` 이 그대로 있어야 합니다.

> 첫 접속이 30초에서 60초 걸릴 수 있습니다. 무료 서버가 자고 있다가 깨어나는
> 시간입니다. 흰 화면에서 한참 기다리는 게 정상입니다.

여기까지 되면 **앱은 완성**입니다. 남은 건 주소 연결뿐입니다.

이 시점에 Render 주소를 메모장에 적어 두세요. 8단계에서 씁니다:

```
sheetzi-xxxx.onrender.com      ← https:// 는 빼고, 이 부분만
```

## 8단계 — Cloudflare 에 DNS 레코드 추가

1. <https://dash.cloudflare.com> 로그인 → **`xotks.li`** 선택
2. 왼쪽 메뉴 **`DNS`** → **`Records`** → **`+ Add record`**
3. 이렇게 채웁니다:

   | 칸 | 값 |
   |---|---|
   | **Type** | `CNAME` |
   | **Name** | `@` |
   | **Target** | `sheetzi-xxxx.onrender.com` (7단계에서 적어 둔 것) |
   | **Proxy status** | **`DNS only`** (회색 구름). 지금은 반드시 회색! |
   | **TTL** | `Auto` |

4. `Save`

`@` 는 "도메인 그 자체", 즉 `xotks.li` 를 뜻합니다.
원래 DNS 규칙상 도메인 최상단에는 CNAME 을 못 쓰지만, Cloudflare 는 이걸 알아서
처리해 줍니다. 그냥 위 표대로 넣으면 됩니다.

**`www.xotks.li` 도 쓰고 싶다면** 같은 방식으로 하나 더 만듭니다.
Type `CNAME`, Name `www`, Target 은 똑같이, Proxy status 도 똑같이 `DNS only`.
(9단계에서 Render 에도 `www.xotks.li` 를 같이 등록해야 합니다.)

> **왜 지금은 회색 구름(DNS only)인가?**
> 주황 구름(Proxied)을 켜면 `xotks.li` 가 Cloudflare 의 주소를 가리키게 됩니다.
> 그러면 9단계에서 Render 가 "이 도메인이 정말 내 서비스를 가리키나?" 를 확인하고
> 인증서를 발급하는 과정이 실패할 수 있습니다.
> **인증서를 먼저 받고, 그다음에 주황 구름을 켭니다.** 순서가 중요합니다.

## 9단계 — Render 에 도메인 등록하고 인증서 받기

1. Render → 해당 서비스 → 왼쪽 메뉴 **`Settings`**
2. 아래로 내려 **`Custom Domains`** → **`+ Add Custom Domain`**
3. `xotks.li` 를 넣고 `Save`
   (`www` 도 쓸 거면 `www.xotks.li` 도 같은 방식으로 추가)
4. 목록에 뜬 도메인 옆 상태를 봅니다.
   - `Verifying...` 또는 `Certificate pending` — 기다립니다. 보통 1분에서 10분, 길면 30분.
   - **`Certificate Issued`** (초록색) — 성공입니다.
5. `https://xotks.li` 를 브라우저에서 열어 봅니다.
   자물쇠가 달린 채로 **로그인 화면**이 나오면 성공입니다.

30분이 지나도 `pending` 이면:

- 8단계의 Proxy status 가 정말 **회색 구름**인지 다시 확인
- Target 에 오타가 없는지 (`https://` 를 같이 붙여 넣지 않았는지) 확인
- Cloudflare 에 `xotks.li` 를 가리키는 **다른 A 레코드나 CNAME 레코드가 남아 있지
  않은지** 확인. 있으면 지웁니다. 같은 이름에 두 개가 있으면 충돌합니다.

## 10단계 — Cloudflare SSL/TLS 모드 (Flexible 절대 금지)

이제 Cloudflare 를 앞에 세울지 정합니다. 두 가지 길이 있습니다.

### 길 A — 회색 구름 그대로 두기 (권장, 그리고 이미 끝난 상태)

9단계에서 `Certificate Issued` 를 봤다면 **이미 다 된 것입니다.**
브라우저와 Render 사이가 Render 의 인증서로 직접 암호화되고, Cloudflare 는 주소만
알려 주는 역할을 합니다.

- 장점: 단순하고, 인증서 갱신이 앞으로도 알아서 됩니다. 고장 날 구석이 적습니다.
- 단점: Cloudflare 의 캐시와 방어 기능은 안 씁니다.

**여기서 멈춰도 목표(HTTPS + 비밀번호)는 100% 달성입니다.**
Cloudflare 의 방패가 꼭 필요한 게 아니라면 길 A 를 권합니다.

### 길 B — 주황 구름 켜기 (Cloudflare 를 앞에 세우기)

**반드시 이 순서로 하세요. 순서를 바꾸면 비밀번호가 암호화 없이 오갑니다.**

1. **먼저** Cloudflare 왼쪽 메뉴 **`SSL/TLS`** → **`Overview`** 로 갑니다.
2. 암호화 모드를 **`Full (strict)`** 로 바꿉니다.
3. **그다음에** `DNS` → `Records` 에서 8단계의 레코드를 편집해
   Proxy status 를 **`Proxied`(주황 구름)** 로 바꿉니다.
4. `SSL/TLS` → `Edge Certificates` 에서 **`Always Use HTTPS`** 를 **켭니다.**
5. `https://xotks.li` 를 다시 열어 로그인까지 되는지 확인합니다.

### 절대로 `Flexible` 을 고르지 마세요

| 모드 | 브라우저 ↔ Cloudflare | Cloudflare ↔ Render | 판정 |
|---|---|---|---|
| **Flexible** | 암호화됨 | **암호화 안 됨** | **금지** |
| **Full** | 암호화됨 | 암호화됨 (인증서 검사 안 함) | 가능 |
| **Full (strict)** | 암호화됨 | 암호화됨 (인증서 검사 함) | **이걸 쓰세요** |

`Flexible` 은 브라우저에는 자물쇠를 보여 주면서, **Cloudflare 와 Render 사이 구간은
평문으로 보냅니다.** 그 구간을 지나는 것에는 **로그인할 때 입력한 비밀번호와
로그인 쿠키가 그대로 들어 있습니다.** 자물쇠가 보인다고 안전한 게 아닙니다.

게다가 Render 는 평문 접속을 HTTPS 로 되돌려보내기 때문에, Flexible 로 두면 보통
브라우저가 **`ERR_TOO_MANY_REDIRECTS`(리디렉션이 너무 많습니다)** 를 띄우며 아예
열리지 않습니다. 그 화면이 보이면 십중팔구 이것입니다.

> 시트지는 앞에 프록시가 있어도 접속이 HTTPS 인지 제대로 알아냅니다.
> 그래서 `Full (strict)` 로 두면 로그인 쿠키에 `Secure` 표시가 붙어 평문으로는 절대
> 전송되지 않습니다. 이건 실제로 확인했습니다.

> 길 B 를 골랐다면 한 가지만 기억하세요. 나중에 Render 인증서가 갱신되지 않아
> 사이트가 안 열리는 일이 생기면, 회색 구름(DNS only)으로 잠시 되돌리고 Render 에서
> 인증서가 다시 발급되기를 기다린 뒤 주황 구름으로 돌아오면 됩니다.

## 무엇이 잘못될 수 있나

### 1. 무료 요금제는 잠듭니다 (가장 자주 겪을 일)

Render 무료 요금제는 **15분 동안 아무도 접속하지 않으면 서버를 잠재웁니다.**

**무엇이 보이나**

- 오랜만에 `https://xotks.li` 를 열면 **흰 화면으로 30초에서 60초** 멈춰 있습니다.
  브라우저 탭에는 빙글빙글 도는 표시만 나옵니다. 오류가 아닙니다. **기다리면 뜹니다.**
- 너무 오래 걸리면 Cloudflare 나 브라우저가 먼저 포기해서 오류 화면이 나올 수 있습니다.
  그럴 땐 **F5 를 한 번 더** 누르세요. 두 번째는 대개 바로 뜹니다.
  (첫 요청이 서버를 깨워 놨기 때문입니다.)

**이건 고칠 수 없나**

유료 요금제로 올리면 잠들지 않습니다. "외부에서 주기적으로 찔러서 깨워 두는" 방법도
있지만, 무료 월 사용 시간(계정당 750시간)을 거의 다 쓰게 되고 Render 가 권장하지
않습니다. **잠드는 걸 받아들이는 쪽을 권합니다.** 데이터는 Supabase 에 있으므로
잠들어도 아무것도 잃지 않습니다.

### 2. 편집 중에 연결이 끊기면 (실시간 연결)

서버가 잠들거나 다시 시작되면 **열려 있던 실시간 연결(WebSocket)은 끊어집니다.**

**무엇이 보이나**

- 헤더의 연결 표시가 `연결됨` 에서 **`오프라인`** 으로 바뀝니다.
- 저장 표시가 `저장됨` 에서 **`저장 대기 중 (3)`** 처럼 바뀝니다. 괄호 안 숫자는
  아직 서버에 못 보낸 변경의 개수입니다.
- 계속 타이핑해도 됩니다. 숫자가 올라갈 뿐입니다.

**입력한 게 사라지나 — 아니요.**
못 보낸 변경은 브라우저 안에 보관되고, 브라우저가
**0.5초 → 1초 → 2초 → 4초 → 8초** 간격으로 계속 다시 연결을 시도합니다.
서버가 깨어나면 자동으로 다시 붙어서 보관해 둔 것을 전부 보냅니다.
그때 표시가 `저장 중…` 을 거쳐 `저장됨` 으로 돌아옵니다.

**단 하나 주의:** `저장 대기 중 (N)` 인 상태에서 **탭을 닫으려고 하면 브라우저가
"나가시겠습니까?" 를 물어봅니다. 거기서 "머무르기" 를 고르고, `저장됨` 이 될 때까지
기다린 뒤에 닫으세요.** 억지로 닫아도 대부분 브라우저에 남아 있다가 다음에 열 때
보내지지만, 브라우저 데이터를 통째로 지우면 같이 사라집니다.

### 3. 사이트가 아예 안 뜬다 — 순서대로 확인

**먼저 Render 주소로 확인합니다.**
`https://sheetzi-xxxx.onrender.com/healthz`

- **여기가 뜬다** — 앱은 멀쩡합니다. 문제는 도메인이나 Cloudflare 쪽입니다. 아래
  "도메인 쪽 증상별 해결" 로 가세요.
- **여기도 안 뜬다** — 앱 문제입니다. 아래 로그 표로 가세요.

**Render → Logs 를 열고, `[시트지]` 로 시작하는 줄을 마지막에서부터 열 줄쯤 읽습니다.**

> **한두 줄 위**에 있습니다. 특히 Supabase 쪽 실패는 원인이 세 가지인데 **마지막 줄이

| `[시트지] 접근 제한 설정이 잘못되었습니다: SZ_PASSWORD_HASH 형식이 올바르지 않습니다...` | 1단계의 `scrypt$...` 줄이 잘렸습니다. **끝의 `=` 까지 전부** 다시 복사해서 넣으세요 |

| 로그에 `[시트지]` 줄이 하나도 없거나 `npm ERR!` | Build Command 가 `npm install` 이 맞는지, Branch 이름이 맞는지 확인 |

> 좋은 소식: **설정이 잘못되면 서버는 켜지지 않고 이유를 말합니다.** 반쯤 동작하는
> 상태로 조용히 넘어가지 않습니다. 다만 그 이유는 **마지막 한 줄이 아니라 마지막 몇 줄
> 안에** 적혀 있습니다. 마지막 줄만 읽고 판단하지 마세요.

**도메인 쪽 증상별 해결**

| 브라우저에 보이는 것 | 원인과 해결 |
|---|---|
| `ERR_TOO_MANY_REDIRECTS` | Cloudflare SSL/TLS 가 **Flexible** 입니다. `Full (strict)` 로 바꾸세요 (10단계) |
| Cloudflare **Error 522** (Connection timed out) | Render 서버가 자고 있어 깨는 데 오래 걸립니다. 20초 뒤 F5. 계속되면 Render 주소로 먼저 확인 |
| Cloudflare **Error 523** (Origin is unreachable) | 8단계 CNAME 의 Target 오타. `sheetzi-xxxx.onrender.com` 을 정확히 확인 |
| Cloudflare **Error 1001** 또는 `DNS_PROBE_FINISHED_NXDOMAIN` | DNS 레코드가 없거나 Name 이 `@` 가 아닙니다. 8단계를 다시 |
| Render 의 **"Not Found"** 회색 페이지 | Render 에 커스텀 도메인이 등록되지 않았습니다. 9단계를 다시 |
| 자물쇠 대신 **"안전하지 않음" / 인증서 경고** | 9단계에서 `Certificate Issued` 가 아직 안 됐습니다. 회색 구름으로 두고 기다리세요 |

### 4. 사이트는 뜨는데 비밀번호를 안 물어본다

Render → Logs 에서 `[시트지]` 로 시작하는 **첫 줄**이 `접근 제한이 꺼져 있습니다` 일 것입니다
(그 바로 다음 줄은 `공개된 곳에서 운영한다면 ... 설정하세요` 입니다).
`SZ_PASSWORD_HASH` 가 Environment 에 없거나 이름 철자가 틀렸습니다.
**지금 인터넷에 무방비로 공개된 상태입니다. 즉시 고치세요.**

### 5. Supabase 무료 프로젝트가 일시정지된다

Supabase 무료 프로젝트는 **일정 기간 아무 활동이 없으면 자동으로 일시정지(paused)**
됩니다. 그 상태에서 Render 가 다시 시작되면 서버는
`Supabase 에 연결하지 못했습니다` 를 남기고 켜지지 않습니다.

**문서는 사라지지 않았습니다.** Supabase 대시보드에서 프로젝트를 **Restore** 하고,
Render 에서 `Manual Deploy` → `Deploy latest commit` 을 누르면 그대로 돌아옵니다.

### 6. 여러 사람이 동시에 쓰는데 가끔 느리다

Render(Singapore) 와 Supabase 사이를 오가느라 편집 한 묶음마다 왕복 시간이 듭니다.
Supabase 프로젝트 지역이 한국, 일본, 싱가포르 근처가 아니면 눈에 띄게 느려집니다.
지역은 나중에 못 바꾸므로, 새로 만들 일이 있으면 가까운 곳을 고르세요.

### 7. 지금 상태에서 안 되는 것들 (미리 알아두세요)

- **인스턴스를 여러 개로 늘리면 안 됩니다.** 무료 요금제라 늘릴 일도 없지만,
  이 프로그램은 한 대에서 도는 것을 전제로 만들어졌습니다.
- **비밀번호는 하나뿐입니다.** 사람별 권한 구분이 없습니다.
- **`data/` 폴더의 기존 문서는 Supabase 로 자동으로 옮겨지지 않습니다.**
  옮기는 도구는 일부러 만들지 않았습니다. 내용을 옮기려면 두 창을 나란히 열고
  `Ctrl+A`, `Ctrl+C`, `Ctrl+V` 로 직접 복사하세요. 무엇이 따라가고 무엇이 안 따라가는지는
  README 의 "Supabase 로 바꾸면 기존 문서는 어떻게 되나요" 에 정리되어 있습니다.

## 나중에 값을 바꾸거나 다시 배포할 때

### 코드를 고쳤을 때

GitHub Desktop 에서 `Commit to main` → `Push origin`.
Render 가 알아서 다시 배포합니다. 끝나면 **Logs 를 다시 한 번 확인**하세요.

### 비밀번호를 바꾸고 싶을 때

1. 1단계를 다시 해서 새 `scrypt$...` 한 줄을 만듭니다.
2. Render → `Environment` → `SZ_PASSWORD_HASH` 값을 바꾸고 저장합니다.
3. 저장하면 자동으로 다시 배포됩니다. **모든 사람이 로그아웃되고 새 비밀번호로
   다시 로그인해야 합니다.** 그게 정상이고, 비밀번호를 바꿨을 때 원하는 동작입니다.

### 배포가 언제 끝났는지 확인

Render 화면 위쪽 상태가 `Live` 가 되고, Logs 끝부분에 `서버 실행 중` 과 그 다음 줄
`클라이언트 버전` 이 나오면 끝입니다 (`클라이언트 버전` 이 마지막 줄입니다). 배포에 실패하면 Render 는 **이전에 잘 돌던 버전을 그대로 유지합니다.**
사이트가 갑자기 죽지는 않습니다.

### 서버를 껐다 켜도 안전한가

안전합니다. Render 는 종료할 때 서버에 정리할 시간을 주고, 시트지는 그 신호를 받으면
`SIGTERM 수신 — 저장 후 종료합니다.` 를 남기고 하던 저장을 끝낸 뒤 내려갑니다.
설령 그럴 틈도 없이 강제로 꺼져도, 이미 `저장됨` 으로 표시된 내용은 데이터베이스에
들어가 있으므로 남습니다. (이 문서를 쓰면서 실제로 서버를 강제 종료한 뒤 다시 켜서
확인했습니다.)

## 부록 A — 환경 변수 전체 목록

시트지가 읽는 이름은 **여덟 개가 전부**입니다. 다른 이름을 넣어도 무시됩니다.

| 이름 | Render 에 넣나? | 안 넣으면 |
|---|---|---|
| `PORT` | **넣지 마세요** | Render 가 자동으로 넣습니다 |
| `SZ_PASSWORD` | **넣지 마세요** | `SZ_PASSWORD_HASH` 를 쓰므로 필요 없습니다 |
| `SZ_PASSWORD_HASH` | **필수** | **비밀번호 없이 전부 공개됩니다** |
| `SZ_SESSION_SECRET` | **필수** | 서버가 다시 시작될 때마다 모두 로그아웃됩니다 |
| `SZ_SESSION_DAYS` | 선택 | 14일 |
| `SUPABASE_URL` | **필수** | **파일 방식으로 켜지고 문서가 사라집니다** |
| `SUPABASE_SERVICE_KEY` | **필수** | 서버가 안 켜집니다 (이유를 로그에 남깁니다) |
| `SUPABASE_SCHEMA` | 선택 | `public` |

> **`SUPABASE_SERVICE_KEY` 라는 이름에 대하여.** 이름은 예전 키 이름(`service_role`)
> 에서 온 것이지만 뜻은 그냥 **"Supabase 비밀 키"** 입니다. 지금 대시보드가 주는
> `Secret keys` 의 `sb_secret_...` 도, 예전의 `service_role`(`eyJ...`) 도 이 한 칸에
> 그대로 넣으면 됩니다. 시트지가 값의 생김새를 보고 알아서 맞춰 보내므로 형식을
> 알려 주는 설정 같은 것은 없습니다. 넣으면 안 되는 것은 공개용 키
> (`sb_publishable_...` / `anon`) 뿐입니다.

여기에 더해 Render 자체 설정용으로 `NODE_VERSION` 을 `22` 로 넣습니다.
이건 시트지가 읽는 값이 아니라 Render 가 읽는 값입니다.

**모든 값은 따옴표 없이, 앞뒤 공백 없이** 넣습니다.
Render 는 값을 그대로 저장하므로 실수로 붙은 따옴표까지 값의 일부가 됩니다.

배포된 서버에는 `.env` 파일이 **없습니다.** Render 의 Environment 화면이 `.env` 를
대신합니다. 혹시 `.env` 파일이 저장소에 같이 올라가더라도 환경 변수 쪽이 항상
이깁니다. 그래도 `.env` 는 절대 올리지 마세요.

## 부록 B — render.yaml 로 한 번에 만들기 (선택)

**5단계를 이미 했다면 이 부록은 건너뛰세요. 안 해도 아무 문제 없습니다.**

이 저장소 맨 위에는 `render.yaml` 파일이 있습니다. Build Command, Start Command,
Health Check Path, Node 버전을 미리 적어 둔 파일입니다. 손으로 입력할 칸이 줄어드니
오타로 실패할 일이 적습니다.

쓰는 법:

1. Render → `+ New` → **`Blueprint`**
2. 저장소를 고르고 `Connect`
3. 비밀 값 세 개를 물어봅니다. 1단계와 3단계에서 메모해 둔 값을 넣습니다:
   `SZ_PASSWORD_HASH`, `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`
   (`SZ_SESSION_SECRET` 은 Render 가 알아서 임의로 만들어 줍니다. 2단계를 건너뛰어도 됩니다.)
4. `Apply`

그다음은 **6단계부터** 똑같이 진행하면 됩니다.

`render.yaml` 안의 값을 바꾸고 싶으면 파일을 고쳐서 GitHub 에 올리면 됩니다.
`region: singapore` 를 다른 곳으로 바꾸거나, 나중에 `plan: free` 를 유료 요금제 이름으로
바꿔 잠들지 않게 할 수 있습니다.
